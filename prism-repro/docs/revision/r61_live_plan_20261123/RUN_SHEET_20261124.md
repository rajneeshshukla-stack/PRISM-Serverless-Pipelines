## 3a. Predictions recorded before preflight (25 Nov 2026; not results)

These are **predictions**, written before any live record exists. They are not to be revised after the run.

- **Memory.** The frozen controller's offline preview selects **1024 MB in every epoch**
  (`local_verification/preview_decisions.json`). The live decisions depend on measured completions and can differ.
- **Warm per-record miss rate at 1024 MB, 14.5 s deadline** (modelled, warm latency only, no start-up):

  | Model | Prediction | Source |
  |---|---|---|
  | Independent per-stage spread (the frozen controller's own planning model) | **about 0.22%** | `docs/revision/p2_dependence_20261124/vw_by_rho.txt` (0.216%) |
  | P2 shared-stage model (ρ = 0.998, measured on the 21 Nov live run) | **about 3.3%** | the same file (3.283%) |

  - The controller plans with the first; the archived AWS data support the second.
  - At about 300 warm records, the two predictions imply roughly 0.7 and 10 misses, respectively.

**How the observed warm miss rate is reported** (section 4, check 7):
- **Denominator:** the number of **fully warm records**, i.e. records with status SUCCEEDED, all four stages present,
  every stage `cold` = false and `memory_mb` = 1024. Shed, failed and partly cold records are excluded and counted
  separately.
- **Numerator:** those fully warm records whose end-to-end time exceeds 14.5 s.
- **Reported per arm,** as misses / fully warm records, with a 95% Clopper-Pearson interval. Records at any other
  memory size are reported separately with their own denominator.
- **Also given:** the same count on AWS-side `service_s` (decision P9). The model's latency excludes the client-side
  path.

## 5. Recovery

- **Interrupted run:**
  `$PY -m prism_pipeline --region us-east-2 teardown --manifest $OUT/manifest.json --execute`. It deletes the
  provisioned-concurrency configs first and keeps the log groups unless coverage is complete.
- **Incomplete coverage:** `collect --manifest $OUT/manifest.json --execute`, then `--rescan` for late lines; then
  `coverage --run $OUT`.
- **Afterwards:** `cleanup-logs --manifest $OUT/manifest.json --execute`. It refuses while coverage is incomplete.
- **A failed arm is not resumable.** Keep its folder, and start a new `$OUT`.

## 6. What the planned sample can and cannot support

The run is one trace-week replay: 323 records per arm, 8 decision epochs of 5 minutes, one run.

| Intended statement | Supported by this run? |
|---|---|
| PRISM's actual controller drives a real four-stage Lambda/Step Functions deployment, and its decisions are actuated (memory, provisioned concurrency through an alias) and logged | **Yes, as a small-scale demonstration** |
| Activation lag of provisioned concurrency on AWS | **Small-scale only:** about 9 observations (4 at epoch 0 and about 5 later changes, from the preview), at 10-s polling resolution |
| Cold starts, service times, initialisation types, spill-over to on-demand | **Yes, descriptively**, for this workload and load |
| Per-record deadline attainment per arm | **Imprecise.** With 323 records, 0 misses gives 0-1.14%, 3 misses 0.19-2.69%, and 10 misses 1.49-5.62% (95% Clopper-Pearson) |
| A difference in deadline misses between the arms | **Only if large.** A paired McNemar test has power 0.35 for 3% against 1%, 0.82 for 5% against 1%, and 0.95 for 10% against 3% (simulated, independent misses) |
| The paper's SLA metric (violating 15-minute windows against the 2% target) | **No.** Each 40-minute arm contains 2 complete windows |
| A cost advantage, or cost equivalence, of PRISM | **No.** One run, one trace-week, estimated prices; actual charges need the bill (R2.14(b)) |
| Generalisation to other traces, loads, deadlines or applications | **No** |

**Consequence for the reply.** The R6.1 reply may report the run as a small-scale live demonstration of the
controller and its actuation, with measured latencies, cold starts and activation lags. It must not present it as
validating PRISM's compliance or cost results.

A test of the window-level SLA would need far longer arms. Estimating a violating-window rate near 2% to within a
point needs several hundred windows per arm, i.e. days of live traffic. That is a separate decision.
